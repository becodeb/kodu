# Exploration: `catalogo-de-proveedores`

Split the provider account out of `AiModel` so an API key is stored once and
reused by many models, including the same provider kind configured twice with
two different keys.

## User intent (verbatim request, Spanish)

> "haceme que pueda configurar tanto proveedores como modelos así una sola vez
> guardo la api key y después ya puedo ir eligiendo modelos de ahí, tene en
> cuenta que quiza por ejemplo para un mismo proveedor lo quiero tener dos veces
> una vez con mi api key y quiza otra vez lo quiero tener con otra así voy
> eligiendo. Y los modelos quiero poder elegir de que proveedor pero si queres
> cargo una vez el modelo y le pongo de que proveedor y un fallback o no y así."

Follow-up constraint, same session:

> "y tengo un webhook que se deployea automaticamente así que asegurate que se
> ejecuten las migraciones necesarias automaticamente"

## Current state

`AiModel` (`prisma/schema.prisma:161-213`) conflates three concerns in one row:

1. **The provider account** — `provider` (free-text label), `baseUrl`,
   `apiKeyCipher`, `apiKeyHint`.
2. **The model** — `providerModel`, the three `Decimal` prices,
   `maxOutputTokens`, `maxInputChars`, `supportsVision`, `userTokenLimit`,
   `displayName`, `description`, `adminNote`.
3. **Orchestration** — `enabled`, `selectableByTeacher`, `isDefault`,
   `sortOrder`, and the `fallbackModelId` self-relation (`@relation("Respaldo")`).

`@@unique([provider, providerModel])` is what forbids the exact thing the user
is asking for: the same provider label and the same provider-side model id
configured twice against two different accounts.

Encryption (`src/lib/crypto/secretos.ts`) is AES-256-GCM, serialized as
`v1.<nonce>.<ct>.<tag>` in base64url. **The AAD is always the `AiModel.id`**
(secretos.ts:99-114), and the id is generated by the caller with `randomUUID()`
*before* encryption (`src/pages/api/admin/models/index.ts:64-75`). A ciphertext
is therefore cryptographically bound to the row id it was created against; the
module's own docstring states that moving a ciphertext to another row must fail
loudly. That is a deliberate security property, not an accident.

## Hard deployment constraint (verified, decisive)

Production deploys via a Coolify webhook on push. `docker/prod-entrypoint.sh`
runs `npx prisma migrate deploy` and then starts the server — migrations are
already automatic and idempotent (Postgres advisory lock, safe with replicas).

But the runtime image cannot run a TypeScript backfill script:

- `Dockerfile:50` — `RUN npm ci --omit=dev`, so `tsx` (a devDependency) is absent.
- `Dockerfile:52-56` — only `dist`, `prisma`, `prisma.config.ts` and
  `docker/prod-entrypoint.sh` are copied into the runner. **`scripts/` is not
  in the image at all.**

`scripts/rotar-clave.ts` is therefore an operator-run tool (`npx tsx` on a dev
machine against the prod DB), not something the deploy can execute.

**Consequence: the data migration for this change must be pure SQL, or the
Dockerfile and entrypoint must grow a new stage to carry and run a script.**
The first option is strongly preferred — it keeps the deploy story unchanged and
removes the highest-risk artifact in the change.

## The AAD problem and the approach it forces

Moving `apiKeyCipher` to an `AiProvider` row changes the AAD from
`AiModel.id` to `AiProvider.id`, which breaks decryption of every stored key.

| Approach | Verdict |
|---|---|
| **(a) `AiProvider.id` = the id of the anchor `AiModel` it inherits the key from** | **Chosen.** Pure SQL. The AAD value is unchanged, so the copied ciphertext still authenticates. No crypto runs during the migration at all. |
| (b) TypeScript script that decrypts with the old AAD and re-encrypts with the new one | **Rejected.** Cannot run automatically — `scripts/` and `tsx` are not in the runtime image. Would also put a crypto pass over every live key, whose failure mode is silent key loss. |
| (c) Change the AAD to a stable non-row-id value | **Rejected.** Deliberately regresses the documented "moved ciphertext fails loudly" guarantee, and does not fix historical rows — a migration would still be needed. |

### Making (a) lossless: conservative grouping

The naive grouping rule (one `AiProvider` per distinct `provider` + `baseUrl`)
has a data-loss hole: if two rows in a group hold genuinely different non-null
keys, one key must be discarded and the losing model would then authenticate
against the wrong account. Ciphertext comparison cannot detect this — GCM uses a
random nonce, so two encryptions of the same plaintext always differ.

The fix keeps the migration in SQL and lossless: **merge only when it is
provably safe.**

Group by (`provider`, `baseUrl`), then within each group:

- Rows whose `apiKeyCipher` is NULL carry no secret and can always be folded
  into the group's provider.
- If the group has **at most one** row with a non-null cipher, that row is the
  anchor: the new `AiProvider` takes its `id`, its `apiKeyCipher` and its
  `apiKeyHint` verbatim. The whole group points at it.
- If the group has **two or more** rows with non-null ciphers, do **not** merge.
  Emit one `AiProvider` per such row, each taking that row's own `id` and its
  own cipher. Nothing is decrypted, nothing is compared, nothing is lost.

This is expressible in plain SQL. The worst case is cosmetic — the admin sees
two provider entries that represent the same account and can consolidate them in
the panel by re-pointing the models and disabling the extra. That is a
one-minute cleanup, traded against a crypto backfill whose failure mode is
silent and irreversible.

A group with zero non-null ciphers still needs a provider row; it gets a fresh
deterministic id (there is no cipher to bind, so the AAD is irrelevant).

## Data model split

Moves to `AiProvider`: `baseUrl`, `apiKeyCipher`, `apiKeyHint`, and the
`provider` label.

Stays on `AiModel`: `providerModel`, all three prices, `maxOutputTokens`,
`maxInputChars`, `supportsVision`, `userTokenLimit`, `displayName`,
`description`, `adminNote`, `enabled`, `selectableByTeacher`, `isDefault`,
`sortOrder`, `fallbackModelId`.

`AiModel` gains `providerId` with `onDelete: Restrict`.
`@@unique([provider, providerModel])` becomes `@@unique([providerId, providerModel])`
— which is precisely what unlocks "same model on two accounts".

Open for the proposal phase: whether the provider needs both a stable `kind`
slug and a human `label`, or just one free-text label. Nothing in the runtime
currently branches on the `provider` string — it is purely descriptive today.

## Fallback semantics — unchanged

`fallbackModelId` stays on `AiModel` and `cadenaDeMotores()`
(`src/lib/ai/catalogo.ts:164-191`) needs no logic change: it walks model-to-model
links and treats `ProviderConfig` as opaque. Only `construirConfig()` changes,
to source `apiKey` and `baseUrl` from the joined provider.

Model-level fallback strictly subsumes provider-level fallback for the user's
stated case. "Same model, two accounts, pick primary and fallback" is inherently
a model-to-model relation (model row A on provider 1 falls back to model row A'
on provider 2). A provider-level fallback could not express it without
re-deriving which model to use on the fallback provider — i.e. reinventing
model-level fallback with an extra hop. It also preserves the existing
cross-model chain (M3 → M2.7 → DeepSeek).

## Deletion and disabling

`AiModel` has no DELETE route by design (`src/pages/api/admin/models/[id].ts:13-16`).
`AiProvider` should follow the same precedent, and the FK should be `Restrict`:
`SetNull` would silently orphan models (no key, no base URL) and `Cascade` would
delete models whose ids are still referenced by historical `TokenUsage` and
`Project` rows.

Recommend `AiProvider.enabled` as a genuinely new capability: disabling an
account makes every model on it behave as disabled without flipping each model's
own `enabled` bit, so re-enabling restores each model's prior state.
`catalogo.ts` then checks `fila.enabled && fila.provider.enabled` wherever it
checks `fila.enabled` today. `cadenaDeMotores()` already skips configs without a
usable key while continuing to traverse, so folding provider-disabled into that
same predicate is an extension of an existing mechanism, not a new one.

- `prisma/schema.prisma:161-213` — new `AiProvider`; `AiModel` loses four fields, gains `providerId`.
- New hand-written `prisma/migrations/<ts>_catalogo_de_proveedores/migration.sql` + `migration_down.sql` (both conventions already established, see `20260919000000_catalogo_de_motores/` and `20260920000000_costo_de_turnos/migration_down.sql`). Must be pure SQL and must be picked up by `prisma migrate deploy`.
- `src/lib/crypto/secretos.ts:99-114` — docstrings only; the AAD is now "the id of the row that owns the cipher". No functional change.
- `scripts/rotar-clave.ts` — repoint from `prisma.aiModel` to `prisma.aiProvider`.
- `src/lib/ai/catalogo.ts:34-93` — `include: { provider: true }`; `clavePlano()` decrypts `fila.provider.apiKeyCipher` with AAD `fila.provider.id`; `construirConfig()` reads `fila.provider.baseUrl`; enabled predicates fold in `provider.enabled`.
- `src/lib/admin/modelos.ts:11-60` — `MotorAdmin` gains `providerId` and sources `provider`/`baseUrl`/`tieneClave`/`apiKeyHint` from the join.
- New `src/lib/admin/proveedores.ts` — `ProveedorAdmin` DTO + `serializarProveedor()`, same masking discipline (never `apiKeyCipher`).
- New `src/pages/api/admin/providers/index.ts` (GET/POST) and `[id].ts` (PATCH only).
- `src/middleware.ts:130-134` — the `/api/admin` prefix already covers the new routes; verify, do not assume.
- `src/pages/api/admin/models/index.ts` and `[id].ts` — schemas drop `provider`/`baseUrl`/`apiKey`, gain `providerId`. `orden.ts` untouched.
- New `src/pages/admin/proveedores.astro` + `ProveedoresPanel.tsx` + `ProveedorForm.tsx`, mirroring the existing models panel.
- `src/components/admin/ModeloForm.tsx:54-59,140-239` — provider/baseUrl/key fields become a provider `<select>`; needs an empty state pointing at the providers screen.
- `src/components/admin/ModelosPanel.tsx:190-198` — row display of provider and key hint.
- `e2e/m3-motores.ts:99-131` — the model-creation flow it drives no longer has provider/baseUrl/key fields; needs a provider-creation step first, plus an assertion that `GET /api/admin/providers` never leaks ciphertext.
- `openspec/specs/ai-model-catalog/spec.md:12-25,51-68` — requirements state provider/baseUrl/key live on the model; both need `MODIFIED` deltas, or a sibling `ai-provider-catalog` domain.
- `TokenUsage` and `Project` FKs to `AiModel.id` are untouched. An `AiProvider.id` that numerically equals a source model's id is a different table's PK; there is no collision.

## Open questions for the proposal phase

1. Does `AiProvider.enabled` (account-level cascade disable) ship now, or is disabling each model individually acceptable for v1?
2. Does the provider need a stable `kind` slug distinct from the human `label`, given nothing branches on it today?
3. Separate `/admin/proveedores` screen plus nav item, or tabs inside `/admin/motores`?
4. Are the dead per-engine env vars in `src/lib/env.ts:48-93` (confirmed unread anywhere in `src/`) in scope to remove here, or a separate cleanup?

## Risks

- The migration runs unattended on every deploy. It must be idempotent and must not depend on anything outside `prisma/`.
- `e2e/m3-motores.ts` is the only automated coverage for this surface and needs a real rewrite. The only gate is `npm run check` (tsc-only); there is no unit test runner.
- If the conservative grouping rule is relaxed into "always merge by provider+baseUrl", the change acquires a silent-key-loss failure mode. It must not be relaxed.
